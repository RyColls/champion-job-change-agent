An agent that notices when a champion changes jobs

When someone who champions your product leaves a customer, a renewal is at risk and the person is a warm lead at their next company. This proof of concept catches that moment, decides what it means with plain rules, and puts a human in front of every message before it goes anywhere.

The sample client's starting point

These are the scenario's starting conditions, not results from this project. Cairnboard is a fictional product feedback and roadmap tool with 3,000 paying companies, about 41,000 named users and an average contract of $18,000 a year.

  • About 1 in 5 champions changes jobs each year, roughly 600 moves across 3,000 customers.
  • 4 of the 10 largest accounts that churned last year had lost their champion 60 to 120 days before renewal, and nobody knew.
  • 11 deals last year came from former champions who brought Cairnboard to a new employer. They closed at 36%, against 13% for cold outbound.
  • No system tracked any of this. Customer success managers found out when an email bounced.

What the agent does

One event type comes in: a contact's employment changed. Code verifies it and decides what to do. A model writes three things. A person approves every message.

  1. Read the event
  2. Match the person
  3. Where they went
  4. Duplicate check
  5. Watch list
  6. Rules
  7. Draft and fact-check
  8. Human approval

Rules decide the play, in code, the same way every time, and revenue operations owns them. When the person joined a company that fits and is not a customer, the agent creates the contact, carries over their history and drafts outreach for a rep. When they left a customer account, it raises a risk flag with days until renewal, suggests next contacts and opens a task for the customer success manager. Competitors suppress outreach, and every event, including the ones that led to no action, is logged with the rule behind each decision.

What failed, and why

The first run on the eval feed passed 5 of 9 tests and one name collision triggered a play. A different person with the same first name, at the same customer as a known contact, was matched as a surname change. A surname mismatch alone now carries too little weight to confirm a match, and the fix was checked on a new feed rather than tuned on the one that exposed it. The first-run results are kept in the repository history.

Detection stays below its target: 48 of 55 real departures were caught, against a target of at least 52. Every miss was held in identity review rather than guessed at. These events arrive without a previous employer, so the only evidence is a name, a city and sometimes a title. Real moves and look-alike strangers produce the same evidence. The review queue on this feed held 9 events: 2 collision, 1 moved competitor, 5 moved fit, 1 moved nofit. Lowering the confirm threshold to catch more real moves would also let strangers trigger plays, so the agent holds them for a person. Detection, classification and the old-account play all fail for this one reason, because events held in review never reach the rules.

What would fix it: a stable profile identifier from a data provider, or a second corroborating field such as the previous e-mail domain on every event. Neither is part of this proof of concept.

What changed after the first run

  • Identity rule. A surname mismatch can no longer confirm a match by itself (described above).
  • Generator. The first version could give an account a renewal date earlier than the departure, which produced negative days until renewal in the demo. Renewal dates are now always after the feed. This changed only that field, so the first-run counts above are unaffected.
  • Fact checker. It wrongly flagged a possessive form of a name from the record, and it now also blocks gendered pronouns, because the record has no gender.

How the model outputs were produced

The agent has three interchangeable backends: a deterministic template backend used by tests, a live backend that calls the Anthropic API with the models above, and a recorded backend that replays stored model answers. The build session had no API key, so the live path is covered by unit tests against a fake client and has not run against the real API. The model answers behind the published results were produced by Claude Haiku and Sonnet subagents given the same system prompts as the live backend, then stored and replayed. Each queued draft shows which backend wrote it. One batch of summaries was rewritten after the first attempt turned out to be script-generated, and a no-pronoun rule was added after a draft inferred gender from a name.

What this does not show

  • Any real client, real data or live deployment.
  • Any business outcome. No churn was prevented and no pipeline was generated.
  • A connection to a data provider. The feed is simulated.
  • That the fact checker catches everything. It checks entities, numbers, quantities, pronouns and outcome language. It cannot verify arbitrary lowercase prose, which is why a person reviews every draft.

Run it

pip install pytest, then python -m pytest for the unit tests, python -m agent.cli --feed eval2 --backend template to run the pipeline, and python -m evals.run_acceptance --feed eval2 --backend template for the nine tests. The design is in DESIGN.md.
